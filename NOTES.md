# NOTES

## Assumptions
- **Week in progress**: max `shift_date` in `shifts.csv` is Wed 2026-08-12, so the target week is Mon 2026-08-10–Sun 2026-08-16 (weeks run Mon–Sun as stated).
- **Overtime formula**: reverse-engineered from `weekly_summary.csv` and confirmed exactly — `overtime_hours = max(0, total_hours - 45)`, `breached = overtime_hours > 10`. No exceptions found across 2,122 historical person-weeks.
- **Missing clock-outs** (184 of 8,863 shift rows, spread evenly across the whole period): I confirmed the client's own `total_hours` already treats these as **zero hours worked**, not an open/ongoing shift — I matched this convention exactly so the dashboard stays consistent with existing payroll, but this means both systems likely *understate* some people's real hours and real overtime. Flagged in the dashboard's data-quality note rather than silently imputed.
- **Overnight shifts** (clock-out earlier than clock-in): treated as crossing midnight, +24h. Confirmed against `weekly_summary.csv` totals (exact match, 0 discrepancy across all weeks).
- **Overtime cost estimate** in the dashboard uses 1.5× `hourly_rate` on projected overtime hours only — it does not separate out Sunday/public-holiday hours (which are 2×), so it's a lower-bound estimate, labelled as such.
- The current week partially overlaps a public holiday (10 Aug), which is very likely why hours are running ~8% hot across the board this week versus the historical average — a real signal, not a data artefact (checked total Mon–Wed hours: 4,223 this week vs. ~3,900 average).

## Checking the note-sorting
No answer key exists, so I read a sample myself and compared it to the rule-based output (English/isiZulu/Afrikaans keyword rules + a typo-tolerant fuzzy fallback for the residual bucket):
- **Random sample, n=50** (natural class mix): 50/50 agreed with my own reading.
- **Stratified sample, n=65** (deliberately drew every note still sitting in the "other" bucket, to stress-test the hard cases): 60/65 agreed. All 5 disagreements were notes so heavily misspelled they fell just under the fuzzy-match threshold (e.g. *"stod in for Sithole"*, *"waited for relif, noody came through"*) — all should have been `relief_no_show`. That residual bucket is 5 of 2,117 notes overall (0.2%), so on the full dataset I'd estimate real accuracy at roughly **99%+**, with the honest caveat that both samples are small and I labelled them myself rather than an independent third party.
- One genuinely useful thing the sorting surfaced: several notes read like *"client signed for the extra hours but real reason is relief no-show again"* — a supervisor logging overtime as client-billable when the true cause was an uncovered absence. I added an explicit override so these count as `relief_no_show`, not `client_requested` — otherwise the client/ops split would be biased toward "billable."

## What a trained model would learn that this doesn't
This is a rule-based system end-to-end (regex categories, a frequency-weighted historical baseline, a normal-CDF risk score) — deliberately, because with ~2,100 notes and a 3.4% weekly breach rate there isn't enough labelled signal to train something that would beat clear rules, and the rules are auditable, which matters more here than a few points of accuracy.

What it's leaving on the table: the projection treats each person independently and ignores *why* — a trained model (even simple logistic regression or gradient boosting) could use site-level features (this site had 3 no-show notes last week → elevated risk for everyone on that roster this week), role/shift-pattern interactions, and the note categories themselves as predictive inputs rather than just explanatory ones after the fact. Back-tested against 9 leave-one-week-out folds, the current method gets AUC ≈ 0.82 and roughly 70% recall / 10% precision on breaches at the chosen threshold — a real signal, clearly better than "assume last week repeats" (8% precision) or "never flag" (0% recall), but with a lot of noise, because overtime breaches are driven substantially by *unplanned* events (no-shows, breakdowns) that a person's own history can't predict.

To test a trained version honestly on a few hundred people without fooling myself: keep the leave-one-week-out backtest structure (never let a model see the week it's predicting, or any data from after it), compare its AUC/precision-recall curve against this rule-based baseline on the *same* folds, and specifically check whether it's actually using the note-category features or just re-deriving the historical-hours signal I already have — the risk with 200-ish people and a 3% base rate is overfitting to a handful of chronic offenders and mistaking that for generalisation.
